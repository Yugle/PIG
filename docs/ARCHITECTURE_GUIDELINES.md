## 一、 系统三层架构模型与职责划分

本项目专为树莓派等嵌入式 Linux 算力平台与桌面PIG 实体量身打造，系统自底向上划分为三层，层级单向依赖，严禁反向污染：

```
┌─────────────────────────────────────────────────────────────┐
│                    L2: 技能插件层 (skills/)                  │
│   xiaomi_iot  |  reminder  |  weather  |  pomodoro  | ...   │
│   (独立业务自治、物模型解析、三方 SDK 封装、标准双文件契约)  │
└──────────────────────────────┬──────────────────────────────┘
                               │ 动态注册 & 调度反射
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    L1: 核心引擎层 (core/)                    │
│   agent_reasoner (ReAct)   |  behavior_fsm (舵机/动态眼)    │
│   memory_manager (海马体)  |  evolution_engine (生物钟)     │
│   skill_manager (插件加载器与统一时钟事件中枢)              │
│   (100% 领域无关、无具体业务硬编码、事件分发与认知决策)      │
└──────────────────────────────┬──────────────────────────────┘
                               │ 读写与原子持久化
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                   L3: 状态与数据层 (data/)                   │
│   user_profile | memory | circadian | xiaomi_config | ...   │
│   (结构化数据、缓存、设备凭证、配置索引，纯数据无执行逻辑)  │
└─────────────────────────────────────────────────────────────┘
```

## 二、 架构设计五大核心铁律

### 铁律 1：内核层纯净性（Core is Pure & Domain-Agnostic）
> **`core/` 目录下的任何代码，绝对严禁出现任何特定技能、特定品牌、特定设备的硬编码！**

- **反例（严禁出现）**：
  - 在 `core/agent_reasoner.py` 内部写 `if "扫码" in text: skill = "xiaomi_iot"` 或 `if "天气" in text:`。
  - 在 `core/skill_manager.py` 内部写 `set_alarm`、`set_timer` 的具体解析与逻辑；或把 400 行技能代码模板硬编码在 Python 字典里。
- **正例（必须遵循）**：
  - `core/agent_reasoner.py` 只负责组织 System Prompt、执行 ReAct 观察-思考-行动循环、解析标准 JSON 工具调用、回传 Observation 并生成最终回复。它根本不知道世界上有什么小米设备或天气 API。
  - `core/skill_manager.py` 只负责扫描 `skills/` 目录、动态加载 `main.py`、维护后台时钟调度线程（极轻巡检），所有业务能力（包括闹钟和米家）都只是 `skills/` 下的一个标准插件。
  - 商店目录、配置索引必须放入 `data/`（如 `data/skill_store_catalog.json`），内核仅做异步/动态加载。

---

### 铁律 2：技能插件一等公民标准契约与“2+3”双轮驱动生态（Plugin Contract & Hybrid Ecosystem）
> **所有业务能力（无论是线上拉取还是大模型现场自创）必须统一以标准插件形式组织在 `skills/<skill_id>/` 目录下。彻底淘汰本地数据层伪商店 JSON！**

#### 双轮驱动生态模型（Online Registry + LLM Self-Evolution）:
1. **模式 2（线上开源市场 Online Registry）**：通用高频扩展（如加密货币行情、B站UP主数据、网易云等）通过远端开源仓库拉取标准包安装，速度极快且零 Token 消耗。
2. **模式 3（大模型现场自进化 LLM Self-Evolution）**：主人长尾/私密专属需求（如“阿珍的胃药提醒小助手”），大模型通过 `create_custom_skill` 现场手写 Python 代码，经过 AST 语法合法性检验后动态落盘并即时热加载为永久本能。

每个插件目录必须且仅需包含以下双文件：
1. **`skill.json`（插件元数据契约）**：
   ```json
   {
     "id": "skill_id",
     "name": "技能中文名称",
     "version": "1.0.0",
     "author": "Online Community 或 AI Self-Evolved",
     "category": "分类",
     "description": "面向大模型的技能功能描述（必须清晰指引调用时机）",
     "parameters": {
       "param1": {
         "type": "string",
         "description": "参数含义与示例",
         "default": ""
       }
     },
     "default_behavior": {
       "emotion": "HAPPY",
       "action": "NOD"
     }
   }
   ```
2. **`main.py`（执行入口）**：
   - 必须提供且仅依赖 `def run(**kwargs)` 函数入口。
   - 返回值必须为**人类友好的清晰描述文本**，大模型将直接基于此反馈（Observation）作为后续思考与回答依据。

---

### 铁律 3：诚实透明原则（失败就直接说出来，严禁敷衍掩饰兜底）
> **硬件执行或外部服务失败、超时、离线时，必须如实陈述报错真相，严禁使用任何虚假安慰套话掩饰失败！**

- **被截图钉在耻辱柱上的反例**：
  - 工具报错 `Unable to discover the device 192.168.10.95`，最终回复却是：“*我在听呢，有什么问题尽管跟我说吧！*”
  - 工具报错 `HTTP 401 凭据过期`，最终回复却是：“*稍等，正在为您查询...*”
- **正例**：
  - 工具失败时，直接将原因透传给大模型思考：“*操作未能成功：局域网未发现【台灯 (192.168.10.95)】设备，可能处于离线状态或 IP 已变更。*”
  - 达到最大步数（`max_steps`）时，强制返回底层真实的最后一次 Observation，绝不使用默认客套语。

---

### 铁律 4：复合指令单步直达（避免碎片化多轮死循环）
> **当用户一句话包含多个操作或属性设定时，必须支持在单次技能调用中一步到位，严禁强行拆解成多轮工具交互！**

- **反例**：
  - 用户说：“帮我打开台灯 并把亮度调整到50%”。
  - 拆成：第 1 步开灯 -> 第 2 步设亮度 50% -> 第 3 步查询状态。一旦某一中间步反馈不明确，极易引发大模型反复重试并消耗殆尽 4 步上限。
- **正例**：
  - 技能参数设计为 `device`, `action`, `value`。
  - 第 1 步直接下发 `action="打开", value="亮度50%"` 或 `action="turn_on", value="brightness:50"`。
  - 底层驱动（如 `MiotSpecManager`）一次性组装好开机属性和亮度属性，单次 HTTP 请求同时提交，1 步完成任务并返回：“*已为你将【台灯】打开并将亮度设为 50%！*”。

---

### 铁律 5：中英文与编程标识符双向兼容容错
> **大模型认知推理输出具备多样性，技能内部的意图解析器必须具备中英双语与常见标识符容错。**

- 大模型调用技能时，可能输出：
  - 中文自然语言：`action="打开"`, `value="暖光 2700K"`
  - 英文标准指令：`action="turn_on"`, `value="brightness:50"`
  - 驼峰/下划线指令：`action="set_brightness"`, `value="50"`
- 解析引擎（如 `miot_spec.py`）必须使用正则与关键词池覆盖上述所有格式，绝不能假定大模型只会输出纯中文。

## 三、 目录规范与文件存放位置

```
pig/
├── core/                        # 【L1 内核引擎】100% 领域无关
│   ├── agent_reasoner.py        # 思考推理中枢 (ReAct 闭环机)
│   ├── behavior_fsm.py          # 物理微动作状态机 (微呼吸、注视、表情时序)
│   ├── memory_manager.py        # 海马体短时窗口与长期画像档案
│   ├── evolution_engine.py      # 生物钟学习、夜间反思与作息驱动
│   ├── skill_manager.py         # 插件生命周期加载器与低开销时钟轮询
│   └── audio_service.py         # Edge-TTS / 离线切音音频合成
│
├── skills/                      # 【L2 技能插件】高度自治、热插拔
│   ├── xiaomi_iot/              # 米家全生态通用驱动插件 (含 miot_spec.py)
│   ├── reminder/                # 闹钟、定时器与日程插件
│   ├── weather/                 # 天气与穿衣温感助手
│   ├── news_briefing/           # 早间新闻摘要
│   ├── pomodoro/                # 番茄钟专注陪伴
│   └── dice_roll/               # 娱乐互动小插件
│
├── data/                        # 【L3 数据存储】纯数据持久化
│   ├── skill_store_catalog.json # 技能应用商店精选库元数据与模板
│   ├── reminders.json           # 待触发闹钟任务列表
│   ├── memory.json              # 主人画像、偏好事实与对话记忆
│   ├── circadian_profile.json   # 学习到的用户作息画像
│   ├── miot_specs/              # 本地缓存的小米官方物模型定义文件
│   └── xiaomi_config.json       # 米家设备局域网 Token 与云端 Auth 凭据
│
├── scripts/                     # 【CI 与工程脚本】自动化测试与诊断
│   └── test_all_features.py     # 15 项端到端全功能自动化回归测试套件
│
├── web_sim_server.py            # Web 3D PIG 仿真调试服务
└── main_agent.py                # 树莓派实体机主启动入口
```

## 四、 典型反模式与自检清单（Anti-Patterns & Checklist）

在提交任何代码或完成重构前，逐项检查以下红线：

| 检查项 | 危险反模式 (Anti-pattern) | 正确标准 (Standard) |
| :--- | :--- | :--- |
| **内核纯度** | 在 `core/*.py` 中搜索到了特定技能名字（如 `xiaomi`, `weather`） | 必须为 0 处命中，完全通过动态接口注入 |
| **代码异味** | 在 Python 代码中通过多行字符串硬编码另一段 Python 代码 | 必须抽取为独立的数据文件或标准插件文件 |
| **异常处理** | `except Exception: return "我在听呢，有什么问题尽管说吧"` | 如实返回异常详情与建议措施，严禁伪装 |
| **网络请求** | 发起没有超时限制的 `requests.get/post` 调用 | 必须显式声明 `timeout=5`（外部查询）或 `timeout=60`（LLM） |
| **文件写操作** | 直接 `open(path, 'w').write(...)` 写重要数据文件 | 必须使用 `.tmp` 临时文件 + `os.replace` 原子写入 |
| **技能调用** | 将简单的复合操作拆分成连续 3-4 次串行单动作 | 单步复合下发，1 步完成任务 |

## 五、 持续集成与回归验证（CI & Testing）

> ⚠️ **【开发协同流程铁律】按需测试（用户明确要求时方可测试）**  
> **严禁自己开发完就私自启动测试！** 代码编写、重构或配置修改完成后，应先向主人汇报完成内容与改动点，**仅在主人明确发出“测试/跑一下测试”指令时**，才可执行自动化测试套件。

当主人要求测试时，执行以下命令进行自动化回归验证：

```bash
# 运行全系统 15 项端到端全链路测试
python3 scripts/test_all_features.py
```

### 必须 100% 达标的 15 项核心指标：
1. **Web 3D 仿真工作台视窗** (HTTP 200)
2. **动力学动态 SVG 眼球引擎** (12 种表情时序渲染)
3. **Edge-TTS 拟真语音合成** (字节流校验)
4. **记忆中枢与主人画像档案** (长期事实沉淀与读取)
5. **生物钟作息自学习** (/api/circadian 数据一致性)
6. **动态技能热加载体系** (零重启热插拔)
7. **闹钟与日程生命周期调度** (创建 -> 查验 -> 取消闭环)
8. **天气技能四级容错自动定位** (IP 自动兜底)
9. **米家台灯复合指令 (打开+50%亮度)** (单步完成)
10. **米家台灯色温调节 (暖光 2700K)**
11. **米家台灯关闭指令**
12. **未配置设备诚实拒绝** (严禁口嗨欺瞒)
13. **空输入与静音防御** (状态机安全保护)
14. **端到端 ReAct 单步复合控制闭环** (1 步达成，拒绝多轮空转)
15. **端到端失败如实汇报** (失败就说出来，绝无虚假兜底)
